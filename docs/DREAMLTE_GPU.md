# GPU on the Galaxy S8

The GPU is an ARM Mali-G71 MP20 of the Bifrost generation. This page holds what the port measured, what the kernel driver does, and the next steps.

## Hardware facts

| Item | Value | Source |
| --- | --- | --- |
| Register block | `0x13900000`, 0x5000 | Samsung device tree `mali@13900000` |
| Interrupts | SPI 60 (job), 61 (MMU), 59 (GPU) | same |
| Power domain | PMU `0x164840e0`, status `0x164840e4` | pmucal `g3d_on` |
| GPU clock | ACPM DVFS id 4 (`dvfs_g3d`), 260 to 839 MHz | ECT and device tree |
| CMU_G3D | `0x13800000` | pmucal |
| Coherency | none with the CPU (`COHERENCY_FEATURES` = 0) | run c30b |

## What the loader measured

Run c29 read the identity:

- `GPU_ID` = `0x60a00001`: product `0x6000` (G71), revision r0p0.
- `SHADER_PRESENT` = `0x17771777`: 20 shader cores.
- L2, tiler and job slots are present. `MMU_FEATURES` = `0x2830`.

Run c30b ran two jobs through the loader, with the MMU off:

- Identity mode (`ADRMODE_IDENTITY`) failed with `JS_STATUS` 0x42, `JOB_READ_FAULT`. Do not use it.
- Through our own 4-level AArch64 page tables the job finished: `JOB_INT_RAWSTAT` 1, status DONE, and the value landed in the mapped physical page. The same address without a mapping stayed 0.

The page tables use 4 KiB pages and the entry format of Linux panfrost: table entries with type 3, leaf entries with AF, read and write, outer shareable.

## The kernel driver

`iokit/Kernel/arm/S8Mali.cpp`, generated by `tools/dreamlte/apply-dreamlte.py` from `xnu/dreamlte/S8Mali.cpp`.

Milestone 2a, run on the phone on 2026-10-24 (log `logs/sweetlog-gpu2.txt`):

1. `s8gpu=1` enables the driver. Without the argument the driver does not start.
2. It maps the GPU and PMU registers and switches the G3D domain on if it is off.
3. It reads the PLL back and logs the GPU clock.
4. It soft resets the GPU, then powers L2, the shader cores and the tiler.
5. It builds one address space with its own page tables over a 64 KiB physically contiguous block.
6. It runs two WRITE_VALUE jobs on slot 0 and polls for completion. The first writes through a physical address, the second through a different GPU virtual address that maps to the same page.
7. It checks that a page which is not mapped stays untouched, then powers the GPU down.

Measured on the phone: the driver loaded, the GPU reported ID `0x60a00001`
r0p0 with 20 shader cores, all blocks came ready, and job 1 finished with
`RAWSTAT` 0x1 and the value `0xc0ffee11` in the mapped page. The first run
reported a failure only because it read the wrong status register; that is
fixed. Job 2 and the unmapped-page check run next.

### Milestone 2b, run on the phone on 2026-10-24 (log `logs/sweetlog-gpu6.txt`)

The driver makes buffer objects and runs a job that writes through one of
them. It also runs a job that reads an address with no mapping and checks
that the MMU reports the fault and that the job does not complete:

```
S8 GPU: BO job done RAWSTAT 0x1 header status 0x1 B[0x10] 0x600dcafe
S8 GPU: unmapped job did not complete RAWSTAT 0x0 MMU int 0x1 fault 0x7c0003c3 at 0x12010
S8 GPU: milestone 2b (1/2) passed: BOs and a fault
```

### The user client

`S8MaliUserClient` speaks the panfrost call numbers, so Mesa needs no change
in the call path:

| Selector | Call | What it does |
|---|---|---|
| 0x00 | `GET_PARAM` | ID, revision, core count, features |
| 0x01 | `CREATE_BO` | makes a buffer object, returns a handle |
| 0x02 | `MMAP_BO` | maps it into the client, returns an address |
| 0x03 | `GET_BO_OFFSET` | GPU virtual address of a buffer |
| 0x04 | `SUBMIT` | runs a job chain on a slot |
| 0x05 | `WAIT_BO` | waits for a job that writes the buffer |
| 0x08 | `MADVISE` | accepts the call, does nothing yet |
| 0x80 | `S8_LOG` | copies a string into the kernel log, for tests |

The kernel runs the same calls itself with `s8gpu=3` and checks the result:

```
S8 GPU: user BO 1 size 8192 flags 0 VA 0x13000
S8 GPU: submit ok 1, job 0x13000 slot 1
S8 GPU: UAPI submit 0x0 -> B[0x40] 0x5a5a1234 retained 1
S8 GPU: UAPI test passed
```

Client memory is mapped write-combined. The driver cleans and invalidates
the caches before and after every submit. A fault resets the GPU and the
slot, and later calls still work.

The driver is a user client now. Mesa can talk to it. What is missing is a
`pan_kmod` backend for Darwin, which is in progress.

## Running our own code on iOS 16

A plist in `/Library/LaunchDaemons` or `/System/Library/LaunchDaemons` does
nothing on this system. iOS 16 launchd reads the job table from one file,
`/System/Library/xpc/launchd.plist`, a binary plist whose `LaunchDaemons` key
maps a plist path to the job dictionary. The boot argument
`launchd_unsecure_cache=1` lets launchd use that table without a seal.

So a test job is added to that table, not to the directory:

```python
d = plistlib.load(open('/System/Library/xpc/launchd.plist', 'rb'))
d['LaunchDaemons']['/System/Library/LaunchDaemons/com.s8.gputest.plist'] = {
    'Label': 'com.s8.gputest',
    'ProgramArguments': ['/bin/sh', '-c', 'sleep 10; /usr/bin/s8_test'],
    'RunAtLoad': True,
    'ProcessType': 'Background',
}
plistlib.dump(d, open('/System/Library/xpc/launchd.plist', 'wb'),
    fmt=plistlib.FMT_BINARY)
```

This was found the hard way: a replaced `com.apple.analyticsd.plist` did not
change what ran, because launchd used the copy in the table.

Three more rules came out of the first runs on the phone:

1. `/bin/sh` does not exist on iOS 16. Point the job at the binary itself.
2. A binary must be code signed, even ad hoc (`codesign -f -s -`). Without a
   signature `vm_map_with_linking` refuses region 0 and the process dies with
   signal 9 and `not code signed` in the ring. `amfi_get_out_of_my_way=1`
   does not lift that check here.
3. `write()` to `/dev/console` lands in the kernel log ring. It is the only
   channel from user space that works without the GPU user client, so every
   test line goes there as well.

The user client works from user space. Log `logs/sweetlog-diag1.txt`:

```
s8_test: user client open
S8 USER: s8_test: user client open
S8 USER: s8_test: GPU_PROD_ID 0x6000
S8 USER: s8_test: A handle 1 VA 0x16000, B handle 2 VA 0x17000
S8 USER: s8_test: A at 0x1007f4000, B at 0x1007f8000
```

A chain of WRITE_VALUE jobs does not run on the fragment slot. The same chain
on slot 1 finishes with the value in place.

## Rules

- Do not report success with llvmpipe, softpipe or any CPU renderer.
- Measure the GPU temperature before you raise the GPU clock. The GPU TMU is `tmuctrl_2` at `0x10084000`.
- Keep the G71 errata workarounds from Linux panfrost: TMIX_8463, TMIX_8438 and T76X_3953.

## Known gaps in the driver

Found in the review of 2026-10-24. None of them stops the self test.

1. No interrupts. Completion is polled with 1 microsecond steps, up to 200
   milliseconds. Mesa sends many small jobs, so the job interrupt (SPI 60)
   and the MMU interrupt (SPI 61) are needed next. The S8 has no Mali node
   in the Apple Device Tree, so the node must be added before
   `registerInterrupt` can be used.
2. No fences. A submit returns when the job is done, so a client cannot
   overlap work.
3. Heap buffer objects do not grow on a GPU page fault. Mesa uses them for
   the tiler heap. A fault stops the job and resets the GPU today.
4. Buffer objects are never released when a client closes. The limit is 256
   per boot and the address space is 4 GiB, so this is bounded, not safe.
5. The GPU address space is one space for every client.
6. `GET_PARAM` returns the model id `0x6000` (as Linux does), 1 core group,
   no AFBC and no JS feature bits. Mesa may take simpler paths because of
   that, which is acceptable for the first triangle.
7. The job slot comes from the fragment requirement only: slot 0 for a
   fragment job, slot 1 for everything else.
8. Temperatures come from the GPU TMU with the two-point formula of the CPU
   TMU. The values are logged, not yet enforced.
9. Cache maintenance flushes every mapped buffer before and after every
   submit. Correct, but it grows with the number of buffers.
